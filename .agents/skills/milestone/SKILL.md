name: milestone
description: "Drive one ready milestone through baseline, Codex implementation, sterile cross-vendor review with consented same-vendor or built-in quota fallback, optional numeric verification, archive, plan update, and commit."

Drive exactly one milestone end to end. Argument format: `$milestone M3` or `$milestone M3 plans/other.md`.

Plan path resolution when omitted: use `plans/PLAN.md` if it exists; otherwise, if `plans/` contains exactly one `*.md`, use it; otherwise stop and ask which plan.

Report parsing rule (applies to every stage): an unparseable run never counts as success.
- Missing or malformed `IMPLEMENTER_REPORT` → treat as `blocked`.
- Missing or malformed `REVIEW_VERDICT` → the review run itself is incomplete (infrastructure failure, NOT a code verdict): re-run the reviewer once with the output-contract reminder appended; if still unparseable, stop and surface. This does not consume an implementer revise cycle and is never treated as approve.
- Missing or malformed `NUMERIC_VERDICT` → treat as `unverifiable`, stop and surface.

## Pipeline

**0. Preconditions**

- **Takeover dispatch comes first.** If the tree is dirty, the milestone is already `in-progress`, HEAD is on `ms/*`/detached around milestone work, or matching `.claude/tmp`/`.codex/tmp` implementer artifacts exist, read and use the `takeover` skill. Do not reject or clean the state merely because this Codex session did not create it. The remaining preconditions below are only for a genuinely fresh milestone.
- Resolve the policy project root first: the nearest ancestor of the session cwd containing the active `.codex/hooks/prepare-review-bundle.sh`; resolve it physically, require it to be inside the current Git worktree, and run every relative command below from that directory. In a monorepo this may be below the Git top level.
- Inspect the full Git index from the worktree root before branching. Any staged path outside the policy project root is a stop-and-surface: it belongs to a sibling policy scope and must not be exposed to this milestone's close-out transaction.
- For a fresh milestone, `git status --porcelain -- .` at the policy project root must be empty. Sibling subprojects are outside this policy layer. If the scoped state is dirty, it was misclassified: route to `takeover`, never stash silently.
- Promotion-anchor check + unpromoted-branch scan:
  - `git symbolic-ref --quiet --short HEAD` — if this fails (detached HEAD) or the branch matches `ms/*`, stop and ask: you are not on a promotion target; an unpromoted milestone may be checked out right here and HEAD's plan statuses may be stale or mid-lifecycle. Deliberate linear stacking on the pending milestone is a valid confirmation reason. On confirmation, do not skip stage 2: treat the current HEAD as the human-approved intentional base and still run the scan below anchored at this HEAD — the checked-out ms/* ref itself will be absent from the scan output by ancestry (that absence is covered by this confirmation), but any other unmerged ms/* refs must still be surfaced and individually confirmed. Without confirmation, switch to a named non-ms/* promotion target and restart step 0.
  - Otherwise the current branch is taken as the promotion target (this is an explicit precondition, not an assumption). Run `git for-each-ref 'refs/heads/ms/' --no-merged HEAD` (literal prefix pattern — fnmatch `*` does not cross `/`, so the prefix form is what covers nested refs like `ms/team/M2`) — the command must exit 0 and produce no output; any non-zero exit (e.g. unborn repository) is a stop-and-surface, not a pass. Any listed ref: stop and ask — those branches may hold in-progress or implemented-but-unpromoted work, and HEAD's plan statuses are stale relative to them (risk: duplicate re-run of an already-implemented milestone, or basing a dependent milestone on a base missing its predecessor). Valid confirmation reasons include independent parallel milestones and deliberately parked or rejected branches; never delete or merge those branches yourself.
- Baseline must be green: run each command in `GATE_CHECKS` from `.codex/hooks/gate.conf` (fall back to the gate script's manifest defaults) at HEAD. Any failure → stop and surface it. Required-checks discipline: list only gates that pass at HEAD — either carve the pre-existing debt into its own milestone or adjust gate.conf first. Never start a milestone on a red base.
- Read the milestone section. It must contain: a title, `status: ready`, and a non-empty acceptance criteria list. If status is not `ready` or the criteria are fuzzy, stop and surface the gap. Do not paper over an underspecified milestone.
- **Reviewer-input isolation preflight.** The policy project root's `REVIEW_POLICY.md` must exist, be non-empty, and be a regular non-symlink file. Every convention the reviewer must enforce must be stated in the milestone, `REVIEW_POLICY.md`, or an explicit `review_references` file. Resolve every reference physically before use; require the plan and every review reference to be a regular non-symlink Git-tracked file inside the policy project root. Reject the plan or any reference whose basename is `AGENTS.md` or `CLAUDE.md` or that resolves under `.claude/`, `.codex/`, or `.agents/`. The bundle helper is authoritative for recursive explicit-`@path` import closure and project-declared forbidden paths: it must reject any plan, policy, or review reference in that closure. If the plan cites an agent instruction file as review evidence, stop and have the human move the required facts into the plan or `REVIEW_POLICY.md` before implementation. No reviewer path may receive agent instruction bytes as inputs or open a path listed by the closure manifest; Path C's already-inherited host context is a separately disclosed downgrade, never review evidence.
- **Numeric-preflight.** If the acceptance criteria produce or rely on a headline / decision-relevant numeric result, the milestone MUST carry `numeric: true` (so stage 3's independent verification is not optional). If a milestone yields such a number without it, stop and surface the gap — do not run it under-verified. This determination is about what the milestone produces, nothing calibrates it away.
- Create branch `ms/M<n>-<short-slug>` from current HEAD and switch to it.
- From this point until the close-out commit, the orchestrator itself must not
  modify tracked files: the diff capture in step 2 sweeps the whole working
  tree, and stray edits pollute the reviewed patch. Plan amendments happen
  BEFORE invoking the implementer or AFTER close-out, never mid-run.

**1. Implement**

- Parse and enforce the marker-delimited `IMPLEMENTER_SPAWN_CONTRACT` above as the only spawn authority; prose outside the markers is explanatory. Before dispatch, require the collaboration surface to expose `agent_type`, resolve the nearest `.codex/hooks/prepare-review-bundle.sh` physically with `root="$(cd "$(dirname "$hook")/../.." && pwd -P)"`, and require that root to be inside the Git worktree. Require `$root/.codex` and `$root/.codex/tmp` to be real, non-symlink directories, resolve `$root/.codex/tmp` with `pwd -P`, and require that physical path to equal exactly `$root/.codex/tmp` (never a parent or sibling). Under `umask 077`, create one unique probe with `mktemp "$tmp_real/.implementer-probe.XXXXXX"`, then run the contract's mode commands in order: try `stat -c %a "$probe"` first and try `stat -f %Lp "$probe"` only when the first command exits non-zero. For a command that exits zero, accept only one captured stdout token matching `^[0-7]{3,4}$` and exactly `600`; malformed output or any other mode fails closed. If both commands exit non-zero, fail closed. Delete the probe and verify it is absent; any mismatch stops before dispatch.
- Build a self-contained message with labeled `[MILESTONE ID]`, `[PLAN PATH]`, `[COMPLETE MILESTONE TEXT]`, `[ACCEPTANCE CRITERIA]`, `[ALLOWED PATHS]`, `[OUT-OF-SCOPE CONSTRAINTS]`, `[DURABLE REPORT PATH]`, and `[EXPLICIT IMPLEMENTATION INSTRUCTION]` sections. Embed the complete milestone text and every listed criterion/path/constraint verbatim; never replace any section with a pointer to parent-turn history. Then call `collaboration.spawn_agent` with exactly `agent_type="implementer", task_name="implementer", fork_turns="none", message=<self-contained message>`. The registered `.codex/agents/implementer.toml` profile supplies model and effort; do not pass spawn-time model or reasoning overrides.
- If CLI automation is used, resolve `tmp_real` before launch and grant exactly `--add-dir "$tmp_real"`; never grant its parent, another checkout, or `danger-full-access`.
- The SubagentStop gate enforces the repo's checks and a secrets scan automatically; you do not re-run those here.
- Parse the `IMPLEMENTER_REPORT` from `.codex/tmp/M<n>_implementer_report.md` (the implementer maintains it durably; its final message is a copy, not the original). If `status: blocked` → stop, show the report to the user verbatim, and ask how to proceed.
- If the subagent dies on infrastructure mid-run (connection drop, watchdog stall): its work survives on disk. Inventory the working tree and read the durable report file before doing anything else, then resume with a NARROW finish-and-report instruction (or a fresh agent pointed at the on-disk state). Never restart the milestone from scratch over a lost final message, and never treat infra death as a code verdict.

  0. `mkdir -p .codex/tmp/M<n>/cycle<k>` — the transaction (and the $review reuse of it) must create its directory before any redirection into it; a first-cycle run would otherwise fail before capture and rollback even begin.
  1. Pre-snapshot (exact commands): `command git status --porcelain=v1 -z -- . > .codex/tmp/M<n>/cycle<k>/pre_status.z` and `command git ls-files --others --exclude-standard -z -- . > .codex/tmp/M<n>/cycle<k>/untracked.nul` — the second is the authoritative NUL-safe project-relative list of exactly the paths `-N` will mark (no porcelain parsing).
  2. `command git add -N . && command git diff --no-renames --binary --relative -- . ':(exclude)<plan-doc-path>' > .codex/tmp/M<n>.patch` (the `-N` makes untracked new files visible to diff without staging content; `--no-renames` gives the bundle parser an unambiguous path inventory; `--binary` preserves exact review bytes; `--relative` binds patch paths to the policy project root). - **Path B — same-vendor sterile CLI (fallback-approved only).** Resolve `FALLBACK_REVIEWER_CMD`; default `.codex/hooks/reviewer-codex.sh`. This wrapper uses dedicated `CODEX_HOME` (default `~/.codex-reviewer`), neutral cwd, ignored user config, disabled hooks, ephemeral state, and read-only sandbox. It consumes the SAME immutable bundle and prompt. Path B loses cross-vendor error decorrelation but preserves blank-profile and instruction-file isolation.
- Run Path A or B as `AGENT_KIT_REPO_ROOT=<review_repo_root> AGENT_KIT_REVIEW_BUNDLE=1 AGENT_KIT_REVIEW_BUNDLE_DIGEST=<review_bundle_digest> REVIEWER_CMD_OVERRIDE=<selected-command> .codex/hooks/run-reviewer.sh <prompt-file> <attempt-log>` (per-attempt log `.codex/tmp/M<n>/cycle<k>/attempt<a>/stdout.log`). `REVIEWER_CMD_OVERRIDE` selects exactly one already-resolved tier without mutating gate.conf. The environment values are load-bearing: the wrapper binds the inventory to the expected digest, revalidates every manifest and file hash/mode, and rejects missing/tampered manifests, closure leaks, forbidden paths, writable files, or symlinks. The helper launches the selected command with the prompt as its single argument and closed stdin in its own bounded process group; enforces `REVIEW_TIMEOUT_SECS`; kills and verifies the group on expiry; records `<attempt-log>.exit` and `.pgid`; and cleans up on interruption. Any tool-level ceiling must exceed `REVIEW_TIMEOUT_SECS` plus ~60s or be absent.
- **Path C — built-in Codex reviewer (fallback-approved, last resort).** Enter only after Path B has had its one normal infrastructure retry and remains unavailable. Invoke the registered `reviewer_fallback` custom agent in a fresh context with the EXACT same inlined canonical contract, bundled prompt inputs, fresh nonce, and bundled-patch digest. Save its complete response as the current attempt log and write a separate `completion.status` recording `normal` or the actual agent failure; never fabricate a helper `.exit`. It may read only the named bundle. Path C is not blank-profile isolation—the host has already supplied project instructions—so never describe it as independent; the explicit human consent and archive downgrade are mandatory.
- An attempt enters verdict parsing ONLY if Path A/B's helper reports exit status 0, or Path C's fresh subagent completed normally and its response was durably copied to the current attempt log. A watchdog kill (124), cleanup/quiescence failure (125), interruption (130), any other nonzero/missing CLI exit, or any non-normal/missing built-in completion record is infrastructure failure: archive it with why parsing was skipped and apply the bounded retry rule.
- Parse `REVIEW_VERDICT` from the attempt log. A verdict is valid ONLY when ALL of the following hold — echo-robust parsing; any miss makes the attempt malformed (archive it with the rejection reason, then apply the report parsing rule above):
  - the path-specific completion prerequisite above holds and only the CURRENT attempt's log is read;
  - the LAST verdict block in the log is the one parsed (earlier fragments and prompt echoes are ignored);
  - its `milestone:` equals the current milestone id — a well-formed verdict for another milestone (observed in the field, quoted from an old log) is malformed, not a verdict;
  - its `run_nonce:` and `patch_digest:` equal the tokens generated for this invocation;
  - in standard mode, no maintenance echo is present; in maintenance mode, `review_mode: maintenance`, `maintenance_authorization:`, and `maintenance_digest:` each occur exactly once and equal this attempt's raw authorization and manifest digest;
  - every blocking finding carries exactly one valid `[class]` tag, and the cardinality invariants hold (`approve` ⇒ blocking is exactly the untagged literal `1. none`; `revise`/`reject` ⇒ ≥1 tagged item).
  Then act on the verdict:
  - `approve` → continue to step 3.
  - `revise` → re-invoke the implementer with the blocking list appended — prefer RESUMING the same implementer agent (message continuation) so cycle context carries over; spawn a fresh one only if the original died or its context is suspected contaminated (repeated failure at the same locus is not a fresh-agent trigger: the same-locus rule below stops the blind loop first). Maximum 2 review cycles total; after that, stop and hand both reports to the user. Every cycle that yields a PARSED verdict counts toward the bound; malformed-verdict infrastructure re-runs remain non-counting per the report parsing rule. At the cap, the human may explicitly authorize ONE additional cycle at a time; record each authorization in the run archive (`review_engine.txt`) and plan notes.
    - **Same-locus churn → interactive, not another blind cycle (checked BEFORE the cap).** If two consecutive `revise` cycles keep producing blocking findings at the SAME locus (the same function / analysis / decision-rule) — the reviewer finding a real but progressively finer issue there each time — that locus is intricate judgment-work a blind implementer will churn on, not a spec a fresh pass will close. STOP the blind loop and propose to the human INTERACTIVE rework of that locus (see Never: exploratory/intricate work is interactive by design), or simplifying it to exactly what the milestone pre-registered. Do not spend the cap grinding the same spot. This check fires before the cap decision below.
    - **Severity-aware cap surface (the ask, better-informed — NOT an auto-continue).** When you stop at the cap, group the surviving blocking findings by their reviewer `[class]` tags (as tagged — never re-tagged by you) and present the breakdown, so the human's fix-vs-promote-vs-park decision is one glance rather than a re-read. The cap remains a hard human-control point: you always stop and ask past 2 cycles; the class breakdown speeds the human's decision, it does not authorize continuing without one. (Do not self-assess "the current result is correct" to skip the ask — at the cap the independent numeric verification has not run and self-checks are not evidence, so that condition is not establishable here anyway.)
  - `reject` → stop, surface to the user (the milestone spec itself is suspect).
  - Path A command failed / empty output / no parseable block → apply the report parsing rule above, then stop and ask for fallback consent; never switch silently. Path B failure after its normal retry → Path C under the already-recorded consent. Path C missing/malformed output after one fresh-context retry → stop and surface.
- Record the engine actually used in `review_engine.txt`: `cross-vendor-sterile-cli` or `same-vendor-sterile-cli` with full command, wrapper settings, and emitted fingerprint; or `builtin-fallback (human-approved; same-vendor; project-instruction context inherited)`. Record the primary failure/quota evidence and human consent whenever fallback ran.

**3. Numeric verification (conditional)**

- Only if the milestone has `numeric: true`: invoke the `numeric_verifier` subagent with milestone id and plan path.
- `fail` or `unverifiable` → stop and surface the NUMERIC_VERDICT to the user. Do not proceed.
- **A green implementer self-check is NOT evidence the numbers are right.** An in-repo `--verify` / self-test that passes can encode the SAME convention error as the code it checks (observed: a timestamp-alignment defect whose own `--verify` sampled the identical mis-pairing, so it passed while validating the bug). The `numeric_verifier` — which re-derives from the reference convention WITHOUT importing the milestone's modules — is the gate; a passing self-check is not. Do not report a headline number to the user as settled before the independent verifier passes, no matter how green the gate and self-tests are.

**4. Archive the run**

- Resolve the archive root: `ARCHIVE_ROOT` from gate.conf if set, else the policy project root's `agent_runs/` (gitignored by the kit's install). Resolve it physically (realpath — symlinks and relative segments eliminated) and verify it is either OUTSIDE the worktree or confirmed ignored via `git check-ignore`; fail the archive step otherwise (an archive inside the worktree and not ignored would be swept into the close-out commit). Set `ARCHIVE_ROOT` explicitly when milestones execute in disposable worktrees, so archives outlive them.
- Create `<archive-root>/M<n>/<UTC timestamp YYYYMMDDTHHMMSSZ>/` and save: `task.md` (the verbatim milestone section as given to the implementer), `M<n>.patch` (the final reviewed diff), `review_engine.txt` (engine fingerprint, per-cycle verdicts, the run_nonce/patch_digest and review_bundle_digest tokens, and any human cap-cycle authorizations), per-cycle copies of `instruction-closure.json`, `patch-paths.json`, `omitted-symlinks.json`, and `bundle-inventory.json` (paths/digests only for excluded instructions, never their bytes), and per cycle k: `implementer_report_<k>.md`, `review_prompt_<k>.md`, every attempt's `stdout.log` plus its real `.exit` (Path A/B) or `completion.status` (Path C) — INCLUDING failed/malformed attempts with parser-rejection reasons; plus `numeric_verdict.md` if run. A maintenance archive additionally preserves `maintenance-manifest.json`, every singleton or composite upstream/upgrade attestation JSON at its emitted path (kit-scoped in schema 2), every out-of-band digest, exact base/head/tree, managed union, ownership partition, raw authorization in the prompt/verdict only, and parser validation evidence for all three unchanged maintenance echoes. Before declaring the archive complete, scan the patch, prompt, reviewer output, and archive with the milestone's registered instruction canaries; any hit is fail closed.
- The archive is a local audit artifact: gitignored/outside-tree, never committed. No raw logs beyond the review stdout, no secrets, no bulky outputs.

**5. Close out**

- Update the plan document: set the milestone's status to `implemented`, add today's date and a 1–2 line result note. Update the plan's `## Next` line.
- If any real decision was made during this run (a deviation from plan, a tradeoff taken), record it per the ledger contract in `.codex/hooks/gate.conf` (`DECISION_LEDGER`, default `DECISIONS.md`; `DECISION_LEDGER_MODE`, default `append`): `append` → one line to the named ledger (`YYYY-MM-DD | M<n> | <decision> | <reason>`); `pm-promoted` → the named ledger is human-curated: record in the milestone's `notes:` and draft a `D-NNN`-style proposal in the close-out report instead. The mode governs only the named file — other ledgers in the repo do not change it.
- Stage the exact task paths present in the approved project-relative patch plus the plan and the configured decision ledger when changed. Compare the staged diff to the approved patch plus declared bookkeeping; any sibling-project or extra path is a stop. Immediately before committing, require `git diff --quiet -- <exact reviewed and bookkeeping paths>` so the selected paths have no unstaged drift, then commit only those explicit pathspecs with `git commit --only -m "M<n>: <title> [implemented+reviewed]" -- <exact reviewed and bookkeeping paths>`. The explicit `--only` is mandatory even when the full index was clean at preflight: it keeps a concurrently staged sibling path out of this commit. An unresolved merge, an empty/mismatched pathspec, or any `git commit --only` failure is a stop-and-surface, never a reason to retry with an index-wide commit. Never use `git add -A`: it can sweep sibling, user-owned, or kit-install files into the milestone. Commit messages stay plain and content-focused — no AI/tooling provenance. Do NOT push. Do NOT merge. Promotion is the human's job.
- Final message to the user: branch name, archive path, then the IMPLEMENTER_REPORT and the reviewer's REVIEW_VERDICT verbatim (plus NUMERIC_VERDICT if run).

## Never

- Never loosen or reinterpret acceptance criteria to make a verdict pass.
- Never silently substitute the review engine.
- Never run this pipeline for exploratory research or EDA — that work happens in an interactive session where the human watches intermediate data.
- **But a research/EDA number that CROSSES into a durable or reported output is no longer just "watched" — it must be independently audited before it is leaned on.** The interactive "human watches intermediate data" control audits the *finding*, not the throwaway aggregation/charting code that produced it — a human reading a plausible summary table cannot see a bug in the script behind it (the same failure mode as trusting an implementer's self-check). So when an EDA-derived number becomes (a) a published artifact, (b) a milestone spec's normative context, or (c) a finding the human will act on, it is `unverified-scout` until independently audited, and until then is for interactive discussion ONLY — never quoted as a result, used as a premise, or allowed to set scope, thresholds, criteria, or decisions. Three things count as audited, nothing else does: (i) it traces to an already-audited milestone's output used VERBATIM with no further computation; (ii) any further aggregation/derivation on the durable path has been re-derived through the **`numeric: true` milestone pipeline** — the executable, fail-closed path, since that pipeline runs the SEPARATELY-authored `numeric_verifier` against the source convention; or (iii) it has been re-derived through the **`$review research-audit` gate (P0)** — a pinned P0-b manifest (canonical, content-hashed inputs), a content-bound `audited` AUDIT_VERDICT from the SEPARATELY-authored `research_auditor`, and independent re-derivation from the claim's reference convention (a mere re-run of the author's own script is NOT audited). The author's own fresh-code recompute is NOT independent (same author reproduces the same convention/source-selection error) — it is scout-grade only, exactly as an implementer's self-check is not evidence. So: to publish or act on a research number, promote its derivation into a `numeric: true` milestone (or keep it labelled scout). **Narrow exemption:** EDA that only feeds a later full milestone needs no separate audit ONLY where its number is neither quoted nor used as a premise and does not set that milestone's scope, thresholds, criteria, or hypothesis — the milestone then re-derives it under audit. If a scout number shapes the spec, it must be verified before that spec is frozen. (The interactive path has its own audit without a full milestone: the `$review research-audit` gate — path (iii) above — takes a pinned manifest through the `research_auditor` for a content-bound `audited` verdict.)
